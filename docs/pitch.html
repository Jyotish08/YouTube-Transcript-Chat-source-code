What it does03

Three steps, one paste

From a link to a queryable source.

STEP 01

Paste a link

A YouTube URL, or upload an audio/video file directly. Nothing to install, nothing to configure.

STEP 02

It transcribes and indexes

The transcript is chunked with its timings intact, embedded at 1536 dimensions, and stored in Postgres with pgvector. Progress streams back live.

STEP 03

Ask in plain language

Answers come back grounded in the transcript, each one carrying the timestamps it was built from — clickable, and pointing at the exact second.

One complete workflow, end to end: submit → transcribe → embed → retrieve → answer → verify.

How it works · ingestion06

Originality · resilience

Two independent ways in.

The default route asks Bright Data for a finished transcript — one hop, no proxy, no audio. When that isn't available, the same function walks the long way: proxy the player, download the audio, park it in Storage, and hand Speechmatics a URL rather than a file.

Collections can outlive a single invocation, so a job that doesn't finish in time is parked, not lost — the row keeps its snapshot id and a resume call picks it up exactly where it stopped.

How it works · retrieval07

The insight that makes it trustworthy

Retrieval can't count.

Ask "how many times do they say X" and top-k retrieval will confidently undercount — it only ever saw eight chunks. So that question skips retrieval entirely and reads the whole transcript.

And a literal miss is not proof of absence: ASR writes names phonetically, so a failed word search falls through to semantic search instead of answering "never mentioned" about a video that discusses it at length.

How it was built08

Built without limits

Described in plain language.
Shipped as a production app.

All of Askable — frontend, edge functions, database schema, vector search, the third-party integrations — was built with Native.builder. No boilerplate, no scaffolding by hand: the agents planned, wrote and shipped a real React codebase, and the work went into the parts that actually needed judgment.

Frontend

React + Vite + TypeScript. Submission, live status, chat panel, transcript sources.

Backend

Supabase Edge Functions on Deno — one for ingestion, one for the chat agent.

Data

Postgres + pgvector for chunks and embeddings, Storage for audio, Realtime for status.

Integrations

Bright Data, Speechmatics, AI/ML API — every key held server-side only.

This deck and the architecture behind it were derived from the shipped code, not written ahead of it.
